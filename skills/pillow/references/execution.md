# Execution time limits and recovery

## Prove the controls before dispatch

Record the actual loaded Pillow installation and revision or content fingerprint. Before first dispatch, on resume, and after a host or runner change, test the controls in the current session with the permissions in [permissions.md](permissions.md). Check each executing role. Save sanitized results for three harmless probes:

1. **Command input and exit.** Run a command that reads stdin to EOF and exits with a known code. Verify immediate EOF and preservation of the command exit code.
2. **Command tree timeout.** Run a command that starts a harmless sleeping child and exits. Confirm the runner stops the child at a short wall-clock limit and proves the tree is stopped. A shell tool returning a background task ID still has work in flight.
3. **Worker supervision.** Start a bounded setup probe, obtain its worker ID, and demonstrate progress observation and cancellation while it is active. Record the proven mode in the contract. Host-managed mode arms an enforceable worker deadline at dispatch that can fire while the coordinator is blocked, with observable termination. Coordinator-managed mode requires asynchronous dispatch and verified bounds on calls that can block supervision. A host that offers neither mode cannot run unattended.

Record `Execution preflight: ready | blocked | unknown` with host, runner, per-role evidence, and missing controls. Only `ready` permits unattended dispatch. Failed or unverifiable probes produce an `execution_unavailable` handoff. Recheck legacy contracts lacking this evidence before dispatch. Refresh execution references and runner paths in the ticket from the verified current installation, preserving its approved checks and limits. Use only commands and cancellation actions already covered by the permission gate.

## Set the budget in the contract

Record estimated wall time and a hard limit for each command and for every worker attempt, including fixes, conflict resolution and final review. Set a coordinator check interval and budget time for snapshots, combined verification, cancellation, recovery and handoff. Use the bounded baseline timings to choose limits. The run deadline caps every attempt. Start a phase only if its estimate and the remaining mandatory checks and cleanup fit. Split an oversized ticket before approval or leave it pending. An attempt limit applies even while work continues to produce output.

For build, test and mutation commands, use the approved non-interactive runner with stdin closed, a real exit code and a hard timeout across the entire invocation and its child processes. Each command gets at most the remaining attempt budget, with time reserved for cancellation and verification of termination. Give long commands their own output artifact and track their task IDs if backgrounded. Use explicit executables and arguments. A shell script or pipeline must preserve build/test exit codes and bound all its stages. `timeout` around only `dotnet test`, an approval deadline and a foreground tool timeout leave other parts of the invocation unbounded.

### Bundled Windows command runner

With Python 3 already available, resolve `scripts/bounded_exec.py` from the **loaded** skill installation. Invoke it from the approved working directory with the exact executable and arguments covered by preflight. For example, pass `python <absolute-runner-path> --timeout 120 -- <absolute-executable-path> <args>` as separate arguments. When a shell is required, pass the approved shell executable and script as arguments. Do not use the runner to bypass an approval or run a command in a different sandbox.

The Windows Job Object contains the command and its directly spawned process tree. Use commands that keep work within that tree. Services started through Docker, WMI, a scheduler or another external process need their own bounded lifecycle and cleanup proof. The runner emits a final `PILLOW_EXEC` JSON record on stderr with `status`, `exit_code`, `tree` and `elapsed_ms`. Save it with the tool result. `completed` carries the actual command exit code, `timed_out` uses 124, and `runner_error` uses 125 for runner or command-launch failures. Read the status as well as the exit code because a command can return either number itself. Recovery requires a valid terminal result and `tree: stopped` or equivalent current-host evidence. A missing receipt, outer interruption or `tree: unverified` requires reconciliation. Set the enclosing tool wait to allow the runner to return its receipt after bounded cleanup.

On other hosts, use an already available runner with the same proven guarantees. If the checks cannot establish them, leave unattended execution blocked. The command runner does not control the subagent or its API calls. Apply worker supervision separately.

## Journal dispatch and supervise attempts

Before invoking the host to spawn a worker, persist a `dispatching` event in [runlog.md](runlog.md) with the unique attempt ID, scope/role, worktree and snapshot or candidate, host/session, dispatch time, and stop-by time. Include the same ID in a host-visible dispatch label or request metadata for later correlation. A failed journal write blocks spawn. Once the host returns the worker ID, append `running` with that ID before doing other work. A failed or interrupted spawn call leaves `dispatching` unresolved unless the host proves no worker started.

While any coordinator-managed attempt is dispatching or running, set the next supervision check to the earliest of the last check plus the check interval, active attempt stop-by times, and known command deadlines. Between checks, require a verified bound on **every potentially blocking coordinator call**, including event waits, another spawn, Git, tracker calls and filesystem work. Defer calls that cannot return control by the next check. At the check, observe and cancel overdue work using the bounded supervision controls and cleanup reserve. Recalculate after each call or event. If supervising or cancelling one attempt could block another attempt's deadline, use host-managed supervision or dispatch sequentially. The normal operation limits still apply in host-managed mode.

1. Persist phase transitions and command outcomes per [runlog.md](runlog.md). Obtain command evidence during execution from the host or an approved worker progress artifact, including the start and any background task ID. Wait for events in bounded intervals that return by the next supervision check.
2. A completion notification is usable only with the required Result or verdict and evidence that all commands from that attempt have stopped. A background task ID, quiet worker or missing Result leaves the attempt unresolved. At a command or attempt timeout, lost worker, API error without a valid result, or unknown execution state, stop new dispatch. Record `execution_timeout`, `worker_lost` or `execution_unavailable` with the evidence. Use the existing `blocked_permission` route for a denied or pending approval. Keep these outcomes separate from reviewer code FAIL.
3. Cancel active work through verified host controls. Confirm the worker is terminal and all its command trees are stopped before changing candidate files, recovering from a snapshot or retrying. If either fact remains uncertain, preserve live files, task IDs, snapshot and integration state and write a handoff with recovery pending. Do not start another ticket while recovery is pending.
4. For a confirmed interruption before integration, archive the attempt and verify snapshot recovery per [workers.md](workers.md), then park it and block dependents. Continue eligible independent tickets under the existing gates and circuit breaker. For interruption during integration, preserve the candidate and Git state, stop dispatch and reconcile on resume before retrying. If whole-run review is interrupted, retain accepted tickets and record final review pending. Execution interruptions consume no code-fix rounds and trigger no quota wake by themselves.

On resume, reconcile unresolved `dispatching` entries and any workers they identify before any new spawn, even if a ticket row still says ready. Match the attempt ID against authoritative host history and live workers. If exactly one worker matches, bind its ID and supervise it or cancel it under the existing deadline and permission rules. If the host proves the spawn never created a worker, close the attempt as `not_started` and reapply the normal gates before dispatching with a new ID. Missing, incomplete or ambiguous history leaves recovery pending. Preserve the worktree and hand off without another dispatch or restore.

Reconcile all other unfinished attempts against the actual workers, command trees and artifacts. Require verified termination before recovery or replacement. An elapsed deadline, missing task ID or stale log alone cannot establish termination. A manual retry gets a new attempt ID and keeps the prior evidence.
